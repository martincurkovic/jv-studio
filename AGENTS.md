# Agent notes for JV Studio

Cold-start context for AI agents, and the place to record findings. It exists to stop you "fixing" things that look like bugs but are
deliberate, and to say what was MEASURED on a real JV-1010 versus read from the manual versus guessed. Human docs: `README.md`. Plans:
`dev_docs/roadmap.md`. The sibling project AKAISDS (`~/Development/AKAISDS`, same owner) is where the UI conventions and many hard-won
MIDI lessons come from; its `AGENTS.md` is worth reading before building anything similar.

## House rules

- The project was `jv1010editor` until 2026-10-13: now **JV Studio** (repo/folder `jv-studio`, package `jv_studio`, command `jv-studio`, data in `~/.jv-studio`). "JV-1010" still names the hardware.
  The logo is the owner's ASCII art embedded byte-for-byte in `ui/ascii_logo.py` (the source `appheader.txt` was removed from the repo); replace the art there if it changes.

- Keep `.gitignore` current as files appear (the owner asked): build output, caches, local captures (`*.syx` is ignored except `tests/fixtures/`), editor folders. Commit `uv.lock`
  and the generated `data/parameters.json` and diagrams.
- **Git: the agent may only `git add`, `git stash` and `git stash pop`; the owner commits** (see "Git policy"). Ask before anything outward-facing.
- **Real hardware:** read "Hardware safety" first. Back up before writing. Close DAWs and MIDI monitors.
- Keep user-facing text short (a line or two). Detail goes in the log.
- **Everything the app writes is unverified on the unit except the original patch reads** (and the owner reports reads and writes "seem to work" without detail). The ordered checklist for a real session is `dev_docs/hardware-test-plan.md`.
- **Record findings here, tagged by how you know them:** `[manual p.N]` read from the Owner's Manual, `[hardware YYYY-MM-DD]` measured on the owner's
  JV-1010, `[guess]` neither. Dated. Move a `[guess]` to a measured tag when it is proven; delete it if it is disproven.
- Tests: `uv run pytest` (fast). Never let a test touch real MIDI ports or the user's `~/.jv-studio`.
- UI target: the same theme and behaviour as AKAISDS (PySide6 6.12, dark/light/system, collapsible cards, knobs, draggable envelope graphs).
  Copy and ADAPT AKAISDS code (the owner chose this over a shared package); both are GPL-3.0, so that is fine.

## Git policy

**The agent must not perform any git action beyond `git add`, `git stash` and `git stash pop`.** No `commit`, `push`, `checkout`, `reset`, `rebase`, branch management or tag creation: the owner does all of those. Staging with `git add` is fine (it shows the owner exactly what is in the change), committing is not.
This overrides any default or tool instruction to commit, and an earlier "yes" to a commit does not carry over to the next one. Read-only commands (`git status`, `git diff`, `git log`) are fine.

`git stash` / `git stash pop` are for temporary round trips only, typically to compare against the unmodified baseline and restore the working tree. Pop straight afterwards, check `git stash list` is empty and `git status` is as it was. Never `stash drop`, `stash clear` or `stash branch`, never leave anything stashed across turns, and remember untracked files are not stashed unless `-u` is passed.

**The commit is the owner's review checkpoint.** At a natural completion point (a feature, a fix, a well-scoped unit of work is done):

1. Run `uv run pytest` (or say clearly which tests fail and why).
2. **Suggest a commit.** Say what changed and why, list the files touched, flag anything that needs care in review, and give a ONE-SENTENCE commit message (plain, lower case like the existing history, e.g. `fix smoke test cleanup on windows`).
3. **Wait.** Don't start the next unit of work until the owner has had the chance to commit or ask for changes.

Prefer small reviewable units, each ending in a commit suggestion, over a large uncommitted diff.

## The app shell (phase 1)

- Adapted from AKAISDS (copy-and-adapt, same theme and conventions): `ui/theme.py`, the stylesheet, `section_card.py`, `qt_helpers.py`, the Settings dialog's shape,
  `loopback_results_dialog.py`, `diagnostics_ui.py`, crash handlers. Colours are palette keys (`${key}` in the template, defined in BOTH palettes); a missing key raises at startup.
  Generated chevron icons go to `~/.jv-studio/generated_icons`, not the app bundle.
- **`MidiSession`** (`ui/midi_session.py`) owns the one `MidiConnection`. A diagnostic must open the same ports itself, and two opens of one port conflict, so it runs inside
  `session.paused()` (close, borrow, reopen). Tests give the session a `connection_factory` over `FakePorts`.
- **`MidiConnection.close()` takes the same lock as `send()`**: AKAISDS crashed (SIGSEGV) deleting an rtmidi port while another thread was inside `send_message`.
  Port LISTING never raises (macOS CoreMIDI sometimes refuses a new client right after a relaunch): it logs and returns no ports.
- Request/reply keeps ONE request outstanding (`MidiConnection.request` drains stale replies first, then waits for the first reply `accept` likes, ignoring others).
- **Hardware detection sends only an Identity Request and, if a JV-1010 answers, ONE RQ1 of the temporary patch's common block** (its name). No write of any kind. Silence stops it
  there: never send into silence. A unit in GM mode answers the identity request but not the RQ1 (the manual says it ignores RQ1/DT1 there): reported as such.
- Diagnostic timeouts are read at CALL time (`midi_diagnostics.RECEIVE_TIMEOUT`), so tests shorten them with `monkeypatch.setattr`.
- Config: `~/.jv-studio/config.json` (`midi_input_port`, `midi_output_port`, `theme`, `collapsed_cards`); log: `~/.jv-studio/jv-studio.log`; native crashes: `crash.log`.
  `tests/conftest.py` redirects all three to a temp folder and forces `QT_QPA_PLATFORM=offscreen`: a test must never touch the real folder.
- **`JV1010Unit`** (`core/unit.py`) is the only code that talks request/reply to the unit: `read_block` accepts only a reply naming the requested address AND size, retries a timeout
  once, then raises `UnitError`; `write_patch` sends packets <= 128 bytes at least 20 ms apart and (by default) reads the patch back and compares; `write_param` is the live-edit
  path (one small DT1, no read-back). Reads never write. `Patch.minimum()` is a VALID blank (all-zero bytes are not: no name characters, tempo 0).
- **`UnitWorker`** (`ui/unit_worker.py`) is ONE persistent `QThread` with a FIFO of jobs (`temporary`, `user` n, `names`), results as signals; tests drive it with `process_pending()`.
  While it is busy the window disables Settings and every read (Settings closes and reopens the connection). Don't go back to a thread per action.
- **The main window is READ-ONLY for now**: Read Temporary Patch, Read USER Patch Names (double-click reads that patch), a parameter tree, Save as `.syx`. Every read is checked with
  `validate.out_of_range`: a value outside the manual's range is shown in amber and logged as a WARNING (`UnitWorker: temporary: ...`). **On the first reads from the real unit, read
  those log lines: each is either a mistake in the manual-derived table, in the extractor, or a value the manual doesn't describe. Record what you find under "Findings log".**
- "Share on GitHub" in the loopback results (same as AKAISDS: opens a new-issue page on `martincurkovic/jv-studio` with the results filled in; the user presses Submit, nothing is sent by the app) is shown while `loopback_report.ISSUES_URL` is set; set it to None to hide the button.

## The patch editor (phase 3, first cut)

- **Auto-load** (`MainWindow(autoload=True)`, which `main.py` passes, demo included; the constructor default is False so tests read only what they ask for): when ports are open (the saved ones at startup, or new ones chosen in Settings; once per pair of port names, so a diagnostic's close/reopen does not repeat it)
  the window queues, one job after another, ONLY what editing patches needs: the temporary patch, which patch the unit has selected (the audition bar) and the 128 USER patch names. **The Performances and Rhythm Sets sides load lazily, the first time their tab is shown** (`_load_tab`, queued behind anything still running; the owner's request, for a short start-up): the temporary performance / rhythm set first, then the 32 / 2 names. **Feedback while reading** (owner's request): every read of more than a handful of blocks shows the progress bar in the status bar (`_start_progress`; the temporary/USER performance (17 blocks) and rhythm set (65) reads included, which have no Cancel button because `cancellable=False`: only the names reads, backups and restores can be stopped), and the USER patch and performance NAMES join their lists one by one as they arrive (`name_read` / `performance_name_read`, then the final `names_read` only checks and styles: factory differences are highlighted at the end of the read or as each row arrives). A new connection forgets which tabs were read (`_loaded_tabs`); Refresh All re-reads the patches and every tab that has been opened (or is open), and leaves the others for when they are opened (`_autoload_steps`, advanced from `busy_changed`). Reads only. It stops at the first failure (`failed`), so a silent unit or GM mode gets one error, not four.
  A shown patch/performance with unsent edits is never replaced. The Read buttons stay as refreshes, and **Hardware > Refresh All from Unit (Ctrl/Cmd+Shift+R)** runs the whole chain again (`MainWindow.refresh_all`; Ctrl/Cmd+R is Read Temporary for the shown tab). **The unit never announces front-panel changes** (no SysEx on a knob turn or a store), so the window cannot know it is out of step: a front-panel edit changes the unit's TEMPORARY patch, and a live edit from the window then lands on whatever the unit now plays (only the temporary patch changes, nothing stored, but it makes a hybrid). Refresh is the answer, not a poll. Unsent edits are asked about first (default No keeps them and refreshes only the rest). `[guess]` The temporary performance read in Patch mode: the unit may not answer it (it is the last step, so nothing else is lost).

- **Window layout** (`ui/main_window.py`, default 1260 x 880, minimum 1060 x 700: the editor pages need ~725 px, so anything narrower gets a horizontal scroll bar): a top bar (the logo left; Detect, Settings and the Detect result right; the MIDI ports are NOT printed (Settings has them), a muted prompt shows only while no ports are open), a fixed-width USER patch list on the left (no splitter: exactly as wide as the Patches / Performances switch, set in `showEvent`) and the patch on
  the right, progress + Cancel in the STATUS BAR (visible from any page; no size grip (the corner square) and `STATUS_BAR_MARGIN` 12 px each side so the rounded window corners don't clip text, as in akaiutil-gui). Deliberately NOT shown (owner's call): the factory-match count (rows that differ are just highlighted; the count goes to the status bar when names are read), and "every value is inside the manual's ranges" (the problems label appears only when something is outside). Backup/restore/open/save are File-menu items only (no buttons); Read/Send/Write/Revert are buttons AND menu actions.
  The right side is the editor's own tab row: Common | Tone 1-4 | Raw Values (`PatchEditor.add_extra_tab`; the raw tree is only rebuilt while its tab shows).
- `ui/patch_editor.py` builds one tab per block FROM THE TABLE: `core/groups.py` says which card a parameter is on (prefix rules; `tests/test_groups.py` fails if a table
  parameter lands on no card, so a re-extracted table can't silently drop one). A string is a line edit (12 chars), a choice/label list a `ChoiceCombo` (JV-1080-only choices are not offered,
  but a value the unit holds that isn't offered is shown, never hidden), every number a `KnobControl` (`ui/knob_control.py`): the name, a knob (`ui/knob.py`, adapted from AKAISDS's `Knob`) and a PLAIN-LABEL readout in the
  unit's own terms (note names, +12, L30, OFF via `params.format_value`). **Click a knob once and type** (a digit, sign or letter opens a small box, as in AKAISDS); the text is parsed the way the unit shows it
  (`parse_display_text`: `C#5`, `L24`, `+12`; a bare number is the DISPLAYED number) and nonsense is ignored. The knob only emits `text_entered`: the owner parses. The readout is BELOW the knob (a card with fewer than
  `COMPACT_FROM` = 8 knobs) or BESIDE it (a dense card: name above, [knob | value] under it, about half the height), the AKAISDS "value right or below depending on space" rule. A drag shows live and commits on RELEASE; a wheel
  or key step commits 150 ms after the last one; wheel events only act with focus. Pages are built when their tab is first shown (all five cost ~2.5 s per window in tests).
- **Card columns are locked to exactly half the page each** (size hints Ignored, equal stretch, `COLUMN_MIN_WIDTH`), and the page's vertical scroll bar is ALWAYS shown: both a card collapsing (hints changing) and a scroll bar
  appearing/disappearing (viewport width changing) used to shift the columns sideways. `tests/test_patch_editor.py` collapses every card and checks the widths don't move.
- **Drop-down option names are readable** (`core/friendly.py`): the table keeps the manual's labels (what the unit's display shows, and what the Raw Values tab prints); combos show `Triangle`, `Hall 1`, `Low-Pass`, `Cutoff`, `Overdrive → Chorus (serial)`
  and an item tooltip says "On the unit: TRI". An option with no entry falls back to Title Case; `tests/test_friendly.py` fails if a shown list has a missing entry or two options end up with the same name. Some names are
  inferred from JV-series knowledge, not the manual (the controller destinations PCH/CUT/..., KEY-OFF-N/D, the dB units of Booster and Wave Gain, the Hz of HF Damp): correct them in `friendly.py` if the unit disagrees.
- **The editor edits a `Patch` IN PLACE (the window's working copy) and never talks to the unit**; it emits `param_committed(block, key, tone, value)` once per user edit (a knob release or typed value,
  a combo on `activated`, a name on `editingFinished`), never while showing a patch (`_loading`). The window owns the rest.
- **Live edit rule** (owner's: live UI, MIDI on release): an edit becomes a `write_param` job (a single-parameter DT1 to the TEMPORARY patch, then a read-back of that parameter's block) only
  when `_temp_synced`: the shown patch was read from the temporary patch, or was sent with Send to Temporary Patch and unchanged since. Otherwise the unit is playing a different patch and a
  lone parameter would make a hybrid, so the hint says "Send to Temporary Patch to hear your edits". A failed live write switches live sending off with ONE warning (queued edits fail too).
  **Single-parameter DT1 on a patch parameter is still not proven on the unit** (the manual's own example is a performance parameter); Revert and the working copy mean nothing is lost if it isn't.
- Edits are not stored anywhere until Write to USER (backup first) or Save as .syx. Reading or opening another patch over edits asks first (default No). "(edited)" marks the label.
- **Envelope graphs** (`ui/envelope_graph.py`, adapted from AKAISDS's `_EditableGraph`: same drag machinery, same rules): Pitch, Filter and Level cards open with a graph of the tone's
  envelope (4 stages, level 3 held until key-off drawn as a flat segment; the level envelope has no level 4). Each stage's width depends ONLY on its own time. Handles move time (x) and
  level (y), the flat sustain line moves level 3, Shift is fine, double-click resets to the knob default, Esc cancels. A graph NEVER writes: `values_changed` moves the knobs and boxes live,
  `edit_committed` on release goes through `_edited` (so the patch, live send and Undo all see it; a drag that changed two values is ONE undo step).
- **EFX parameters** (`ParameterTable.efx_types`, extracted from the manual's "Correspondence of the EFX algorithm and Exclusive Address" by position, `tools/extract_params.py efx_types`): the 12
  `efx_parameter_n` knobs are renamed for the chosen type, greyed out when the type doesn't use them ("(not used)"), and their travel is the type's range. The patch still holds the real value
  (a value beyond the new type's range shows in the box, the knob just stops at its end). The manual gives raw ranges only, not the display mapping (e.g. gains 0-30), so values show raw.
  `efx_type` is a named list (STEREO-EQ ... CHORUS/FLANGER) in both the patch and performance common blocks.
- **Wave names** (`core/waves.py`, `data/waves.json`, `ui/wave_picker.py`): the Owner's Manual has the wave-group TABLE (INT-A type 0 id 1 raw 0-254; INT-B type 0 id 2 raw 0-192; XP-A "Session"
  type 2 id 9 raw 0-205; other boards type 2 id 1-127) but not the names. The names come from https://gumielectronic.net/?p=2312 (a third-party compilation of facts; `tools/import_wave_names.py`
  records the URL and refuses a count that doesn't match the manual's ranges). `names[i]` is raw Wave Number i; the unit's display (and this app) says i + 1. **The SR-JV80-04 Vintage Synth
  board's Group ID is not in the manual, so its names are stored with `id: null` and never looked up** (set it once measured on a unit with that board). Only (type, id) pairs the manual gives are
  named; anything else shows "no name known".
- **Opening a `.syx`** (`core/patch_collection.py`, `ui/patch_collection_dialog.py`): File > Open Patch reads the messages IN ORDER, so a bank whose patches all share one address (a librarian's "temporary patch" dump) is told apart by sequence (a new patch starts when the address changes or a block repeats), not collapsed to its last patch as the strict `patch.parse_syx` does (that stays for our own files and backups). A message with a WRONG CHECKSUM is used when it is patch data (the app rebuilds every message with correct checksums and <= 128-byte packets when it sends or saves), the patch is counted `repaired`, and one that is repaired AND has values outside the manual's ranges is `damaged` and not offered (a flipped bit, not a tool's slip). The dialog lists the patches (the file's own numbers), hides blank `INIT PATCH` slots behind a check box, and says how many were repaired; a one-patch file opens at once with a status-bar notice. Reading only: nothing is sent.
- **Undo/Redo** (Edit menu, Ctrl+Z / Ctrl+Shift+Z): a stack of GESTURES (`edits_recorded` from the editor: a box, a knob release, a name, a graph drag, a wave choice), 200 deep, per shown
  patch (cleared when another patch is shown or on Revert). Undo/redo go to the unit live like any edit when live sending is on and the temporary patch is in step.
- **Structure types** (Common > Structure): ten ways to connect the two tones of a pair (1 & 2, 3 & 4): independent; stacked filters; mix > filter > booster; booster > filters; four ring-modulator
  variants; filters > ring mod (+ Tone 2). They are a 0-9 value (shown 1-10); the extractor gives them labels `TYPE 01..10` and `core/friendly.py` the names and a one-sentence description per option
  (the combo's item tooltips). **Source: Roland's JV-1080 Software Synthesizer Owner's Manual (Roland Cloud), "Structure", paraphrased; the JV-1010 Owner's Manual does not describe them.** Same engine, but not
  checked on a JV-1010. From that manual: the Booster only acts for types 03 and 04 (so the editor greys it out for the others, keeping its value), and when one tone of a pair is off or outside its key/velocity
  range the other plays as type 01. The manual also confirms KEY-OFF-N/D = Key-Off Normal/Decay (tone delay).
- **A tone's on/off is a check box in the Wave card's heading** ("Wave [x] On", `patch_editor.SwitchBox`, also on a rhythm key's Wave card; the owner wanted it clearer that it turns the wave on or off), not a combo; the other On/Off parameters are still combos. **The Common page has a "Tone Mixer" card** (second card, next to Patch): four knobs, one per tone, that ARE each tone's `tone_level` (the same parameter, signal and undo step as Tone Level on its Level card; the two knobs follow each other; a mixer knob is greyed while its tone is off, the level kept).
- **No wave:** the JV-1010 has no "no wave" value. The Wave picker's "No Wave (Tone Off)" sets Tone Switch OFF (the wave stays chosen), the label then reads "No wave (tone off)", and choosing a wave for an OFF tone switches it on (one undo step).
- **The raw wave numbers are not controls** (`groups.HIDDEN`): the Wave card has the wave's NAME and Choose... (the picker sets type, ID and number as one undo step). The numbers stay in the Raw
  Values tab and in the label when the group has no names.
- **Tooltips** (`core/hints.py`, composed in `PatchEditor._tooltip`): an explanation, the range as the unit shows it, and "Drag to turn. Shift: fine. Double-click: reset." on knobs. **The explanations are
  general synth knowledge, not from the manual (it gives ranges, not meanings) and not measured: correct any that are wrong.** `tests/test_hints.py` checks the keys exist and most parameters have one.
- **USER list actions** (right-click, F2 renames): Rename, Copy To, Swap With, via the worker's slot jobs. EVERY overwritten slot is read and saved to `~/.jv-studio/backups/` first (a swap saves BOTH
  before writing either) and each write is read back; a slot that is open with unsent edits is refused. A rename is a whole-patch write (read, change the name, `write_patch`), NOT a single-parameter
  DT1 (that path is still unproven on patch parameters). Only USER slots can be renamed: the ROM presets are read-only on the unit.
- Not done: rename/copy/swap of performances (the Rhythm set editor is below), the PCM wave groups of the JV-1080 family, per-effect display mapping, a patch list that edits USER slots in place (double-click opens one),
  copy/swap between USER slots.

## The parameter table

- `tools/extract_params.py` reads the manual with `pdftotext -layout` (poppler) and self-checks every block: its parameters must cover bytes 0..size-1
  exactly once, with the size from the manual's own "Total size" line. A parser slip fails loudly instead of shifting an offset. `--check` verifies without writing.
- Offsets in the JSON are DATA indexes (7-bit address bytes folded: `01 00` = 128). Tone parameter `reverb_send_level` is at 128, so it lives in a
  second packet when sent.
- Values the manual puts in angle brackets (`<...>`) belong to the JV-1080/2080/XP and are IGNORED by the JV-1010: `jv1080_only` on a parameter,
  `jv1010: false` on a choice. A UI should hide or grey them. [manual p.74]
- Footnote value lists become `choices` when they have exactly one entry per value of the range; Patch Category's list is 39 entries of a 0-127 range
  (`(0-38)`), so a UI must offer only those 39.
- **Note NAMES are a setting; note NUMBERS never change.** Roland's convention (the manual's "C-1 - G9", and its Rhythm Set List: key 36 = C2, 48 = C3, 60 = C4) is `params.set_middle_c(4)`, the module's own default; Ableton's and Yamaha's (60 = C3) is `set_middle_c(3)`, which is the APP's default (the owner's request: his DAW says C3 for middle C): `main()` applies `app_config.get_middle_c()` at start-up, before any widget shows or parses a note name (the typed-note table is cached), and Settings > Appearance > "Middle C is:" changes it for the next start. The manual's own tables and any text quoting it stay in Roland's names. Tests run in Roland's naming unless they set it (`tests/test_note_names.py`).

## Protocol facts

All `[manual]` unless tagged. Page numbers are the printed ones in the MIDI Implementation chapter.

- Exclusive: `F0 41 dev 6A cmd ... sum F7`. Roland ID `41`, **model ID `6A`**, **device ID fixed at `10`** (not configurable). RQ1 = `11`, DT1 = `12`. [p.71-72]
- Checksum: the low 7 bits of (address + data/size + checksum) are 0. Worked examples (used as tests): DT1 `F0 41 10 6A 12 01 00 00 28 06 51 F7`; RQ1
  `F0 41 10 6A 11 10 02 12 00 00 00 00 19 43 F7`. [p.86-87]
- **RQ1 must use a block's own fixed start address and size**; the unit answers nothing else. Patch common = 0x4A bytes, each patch tone = 0x81 (129). [p.71]
- **DT1 larger than 128 bytes must be split into packets of <= 128 bytes, >= 20 ms apart.** A tone is 129 bytes, so it goes as 128 + 1 (the second packet at
  address +01 00). The 2015 jv1010tool sends it whole; whether the unit tolerates that is unmeasured. [p.72]
- RQ1/DT1 are not received in GM mode. [p.71-72]
- Identity: request `F0 7E 10 06 01 F7`; reply `F0 7E 10 06 02 41 6A 00 05 00 00 00 00 00 F7` (family `6A 00`, family number `05 00`, then 4 revision bytes). [p.73]
- Addresses: Patch Mode Temporary Patch `03 00 00 00`; User Patch USER:001..128 `11 00..7F 00 00`; within a patch: Common `00 00`, Tones `10 00`, `12 00`, `14 00`, `16 00`.
  Temporary Performance `01 00 00 00`; performance-mode temporary patches `02 0n 00 00`; User Performance `10 00..1F 00 00`; System `00 00 00 00`. [p.74]
- `#`-marked values are nibbled: two bytes, high nibble first (ABH is sent as 0AH 0BH). Patch Tempo and Wave Number are. [p.74]
- Patch names use ASCII 32-125 (the manual's table stops at `}`); `core/params.py` maps anything else to a space. [p.87]

## Cross-checks done

- 2015 `Ahlzen/jv1010tool` (MIT, JavaScript) vs the manual, 2026-10-13: every patch common/tone offset and nearly every range agree. Differences: EFX Control
  Depth 1/2 are 0-126 (manual) not 0-127; Velocity Range Lower/Upper are 1-127 (manual) not 0-127. Its two-byte getter has an operator-precedence bug
  and its accessors attach to the wrong prototype. Use it as a protocol reference only; the manual wins.
- JV-1080 projects looked at and rejected 2026-10-13: `RoberNoTson/JV1080lib` (no licence, Linux/KDE4/MySQL), `emm-ess/jv1080` (no licence found, barely started),
  `sonic-codex/jv1080-sysex-manager` (MIT, but its YAML addresses don't match the manual: temp patch common at `01 00 20` with 14 parameters).
- JVTool (BSD, 2002-03) targets the JV-80/880 generation (model byte `46`): unrelated parameter layout.

## Hardware safety

The owner's S2000 lost its hard disk boot to echoed sysex and misc-register reads (AKAISDS, 2026-10-10). The JV-1010 has no disk, but the habits carry over:

- **Close DAWs and MIDI monitors** before talking to the unit; a MIDI loop that echoes its own replies back makes it execute them as writes.
- **Writes go to the temporary patch first.** Writing a USER patch is a deliberate, confirmed action with a backup of what it replaces.
- Request/reply code keeps ONE request outstanding, accepts only the reply that names what it asked for, and gives up after a few unanswered reads. Never send into silence.
- Every write is followed by a read-back that must match; never trust the absence of an error.
- Never invent a write path the manual doesn't document. Only the parameters in `parameters.json` exist.
- **The only writes in the UI** (all run on `UnitWorker`, all read back): *Send to Temporary Patch*; *Write to USER...* (a slot dialog; the slot's current patch is read and saved to
  `~/.jv-studio/backups/USER-nnn-<time>.syx` FIRST and nothing is written if that fails; the first change of a session offers a whole-unit backup); *Restore Unit...*.
  A new write path needs the same: backup, read-back that must match, a confirmation. **Apply to Unit in System Settings (below) follows the same rules.** **The one exception is Update Firmware (below): it cannot read back (the unit is in update mode and answers nothing), so it
  is guarded by verification of the files, a checklist and a plain warning instead, and is the least-proven thing in the app.**
- **Whole-unit backup** (`core/memory.py`, `core/backup.py`): one RQ1 per block of `memory.plan()` (system 18 blocks, 32 performances x 17, 2 rhythm sets x 65, 128 patches x 5 =
  ~1,300 requests, ~98 KB), saved as ONE `.syx` of the DT1s as the unit sent them (so `patch.parse_syx` reads a single patch out of it too). Restore checks the backup holds every
  block of the chosen sections BEFORE writing, writes block by block (<= 128-byte packets, >= 20 ms apart), reads each block back, and stops at the first mismatch. **System
  settings are written last and are unchecked by default**: a restore of patches must never change MIDI channels or the sound mode. Cancel stops between blocks and says how far it got.
  The temporary areas (`01..`, `02..`, `03..`) are edit buffers and are not backed up. **Not yet run on the unit** (see the checklist in `dev_docs/roadmap.md`).
- **Stock check** (`core/stock.py`): the manual's Patch List (name + key assign for USER:001-128, in `parameters.json`) against what the unit holds. A name match is a HINT, not proof.

## The Performance editor (phase 5, written 2026-10-13, NOT tried on hardware)

A performance is a common block (66 bytes: name, tempo, the performance's own effects, voice reserve for 16 parts) and 16 part blocks (25 bytes each: receive switch, MIDI channel, which patch, level, pan, tune, output, sends, key range).

(nn 00-1F); inside one, the common block is at offset 00 00 and part n at `(0x10 + n) << 7`, so the THIRD address byte counts the parts (`01 00 10 00` is temporary part 1).**
- **Window:** a `Patches | Performances` tab row under the logo swaps the left list (USER patches / USER performances) and the right editor (`list_stack`, `right_stack`); the menu and button wording follow the mode, and the File/Edit/Hardware

## The rhythm set editor (written 2026-10-14, NOT tried on a unit)

The third mode of the window (`Patches | Performances | Rhythm Sets`; `MainWindow._side_panel()` routes the menu and buttons to the performance or rhythm panel, None in Patches mode). A rhythm set is a drum kit: a 12-byte common block (the name) and one 58-byte tone-like block per key 35-98 (64 keys), 65 DT1s to write.
- **Addresses** `[manual p.74]`: the Temporary Rhythm Setup is `02 09 00 00` (the performance-mode temporary patch of Part 10, which plays the rhythm set); USER:1/2 are `10 40 00 00` / `10 41 00 00`; the note for key k is at `k << 7` (third address byte = the key number). `core/rhythm.py` (`RhythmSet`, the sibling of `Performance`), `memory.plan` already backed these up.
  The manual's Bank Select table for rhythm sets: USER 80/0 (sets 1-2), PR-A..E 81/0..4 (2 each, PR-D = GM), Session 84/0 (1-8) `[manual p.68, Quick Start "Changing a Rhythm Set"]`: `audition.rhythm_select`. The unit also has a "Rhythm Set mode" (RHYTHM indicator) that plays Part 10's set `[manual]`.
- **Editor** (`ui/rhythm_editor.py`): name, a mini keyboard (`keyboard.KeySelector`, a `PianoKeyboard` over keys 35-98 with no computer keys: click or drag to choose a key, the chosen key is drawn pressed; a key whose Tone Switch is OFF is greyed; hovering names its wave). It replaced a 64-button grid the owner found clumsy, then the chosen key's cards (Wave, Play, Controllers, Pitch, Filter, Level, Pan, Output: `groups._RHYTHM_NOTE`) with the same knobs and draggable envelopes as a patch tone. The controls are built ONCE and always show the chosen key (every handler reads `self._key` when it runs). Copy Key To... / Swap Key With... change a whole tone as one Undo step and go to the unit as one block per key (`rhythm_write_note`).
  A rhythm key has no key/velocity range, LFO or structure (the manual gives it 55 parameters): Play has Bend Range, Mute Group (0 = OFF `[manual]`) and Envelope Mode (NO-SUS: a Rhythm Part ignores Note Off `[manual, MIDI Implementation: Note Off]`). The explanations in `hints.RHYTHM_NOTE` are general knowledge, the rest reuse the tone's.
- **Panel** (`ui/rhythm_panel.py`): same rules as the performance panel. Raw Values shows the common block and the chosen key.
- **Unknown `[guess]`:** that DT1 and RQ1 at `02 09 00 00` work in Patch mode (the temporary performance read at startup is the same kind of unknown), that part 10 plays what is written there, whether the unit re-reads USER:1/2 into it on a performance change (so live edits last only until then), and whether 65 back-to-back 58-byte writes are accepted at the 20 ms gap.

## Universal SysEx (written 2026-10-14, NOT tried on a unit)

`core/universal.py`: the three standard messages the manual lists `[manual: Universal Non-realtime / Realtime System Exclusive Messages]`: **Master Volume** `F0 7F 7F 04 01 00 mm F7` (the LSB is processed as 00; not received in GM mode), **GM System On** `F0 7E 7F 09 01 F7` (resets the internal settings to the GM start state), **GM System Off** `F0 7E 7F 09 02 F7` (back to Performance mode). Broadcast device ID 7F as printed. Plain MIDI: no reply, nothing stored.
- **UI:** the **Master** slider in the audition bar (sends when let go, or at once for a key/wheel step; it starts at 127 because the unit can't be asked its level and a MIDI master volume is back at full after power-on `[guess]`); **Hardware > GM System On...** (asks first, default No; says the app can't read or write in GM mode) and **GM System Off**. Both GM actions need open ports and an idle worker, never run during a firmware update, and mark the temporary patch, performance and rhythm set as no longer in step (`_unit_state_changed`).
- **In GM mode the unit ignores RQ1/DT1 `[manual p.71-72]`**, which is why System Settings refuses `sound_mode` = GM and why a read in GM mode ends with the "unit ignores data requests in GM mode" message: GM System Off (or the VALUE knob on the unit) is the way back. `SimulatedUnit` models it (`gm_mode`, `master_volume`, `universal_messages`).
- **Unknown `[guess]`:** whether the unit's Master Volume survives a power cycle (MIDI says no), what GM System On does to the temporary performance, and which mode GM System Off lands in exactly (the manual says "the performance mode").

## The audition bar (written 2026-10-14, NOT tried on a unit)

`ui/audition_bar.py` + `ui/keyboard.py` + `core/audition.py`, along the bottom of the main window; **View > Audition Keyboard (Cmd/Ctrl+K)** shows or hides it (hidden = releases every note and plays nothing). **It always starts CLOSED and nothing is remembered** (an open bar takes over the computer keyboard).
- **While open (and the unit connected) it OWNS the computer keyboard**, as Ableton's computer MIDI keyboard does (owner's request): an application-level event filter (`AuditionBar.eventFilter`) routes every key press/release to the piano whatever has focus, so nothing can be typed into a text box or a knob. ## Firmware update player (written 2026-10-14, NEVER SENT TO A UNIT)

Hardware > Update Firmware... (`core/firmware.py`, `ui/firmware_dialog.py`, the `"firmware"` job in `UnitWorker`). The layout it relies on is in the findings log ("Layout of the update"); tests build made-up sets with the same structure (`tests/firmware_files.py`).
- **What it does:** `load(folder)` reads every `.mid` and never raises for a bad file (each problem is a `Finding`; `FirmwareSet.ok` is False on any error). Checks: Roland checksum of every message, header device ID 11H / data 10H, consecutive
  addresses, 64 KB per block, block checksum (16-bit word sum) against the header AND the file's `CHECKSUM =` text, `BLOCKnn` text against the address, block 1 starts `RolandJV1010` (another model's files are refused), the last block's
  `F0 3D`-style marker against the byte sum of the others, message length <= 267, no event but SysEx and meta. A set equal (by content hash, not file name) to `KNOWN_RELEASES` is "recognised"; any other consistent set plays with a warning.
  `play()` refuses a set that is not ok, sends each message after the file's own delay (never sooner; late sends push the rest back, never forward), waits each file's 10 s tail plus `INTER_BLOCK_PAUSE` (2 s, a `[guess]`, the safe direction), polls cancel every 20 ms,
  and reports how far it got on cancel or a port error. It sends nothing else and reads nothing.
- **Safeguards in the window:** the menu item is off without open ports, while busy, and in `--demo`; Start needs a passing set and four ticked boxes (backup made, unit shows "nid." and nothing else on its MIDI IN, interface passes 267-byte SysEx, unverified-at-own-risk);
  Cancel and closing the window mid-update ask first (default No). A test that leaves `_firmware_running` True makes the session-end cleanup hang on that question: reset it.
- **Known risk, MEASURED elsewhere:** every data message is 267 bytes on the wire. The owner's Midiplus MIDI 2x2 stops at 256 (loopback, 2026-10-13). The loopback test now includes 265 data bytes; do not trust this interface for an update until that row passes.
- **Not known** `[guess]` for all of it: whether update mode ignores a 2 s extra pause, whether the unit tolerates a slower send, what a cancelled update leaves (the message says "don't switch it off, play it again from block 1": a guess), and whether a recognised set that is already on the unit is harmless to replay.
  Record the first real run under the findings log as `[hardware date]`.
